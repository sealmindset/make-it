## 0. Method, scope and scoring

### 0.1 Direction

One direction only. **`/make-it` is scored against the playbook.** The playbook is
not scored against `/make-it`. §5 separately records capabilities `/make-it` has
that the playbook does not describe; those are excluded from the score to keep
the denominator stable.

### 0.2 Unit of measurement

The playbook's 14 lessons include `introduction`, `closing-thoughts-and-resources`
and `complete`, which describe no practice. The remaining **12 lessons are the
scorable plays**, listed in §1.

### 0.3 Rubric

Each play receives exactly one verdict. The verdict is a test, not a judgement.

| Verdict | Test | Required evidence | Count |
|---|---|---|---:|
| **Present** | A counterpart exists in the repository and performs the play's function | Path (and line, where applicable) of the implementing file | 4 |
| **Partial** | A counterpart exists but lacks one *named* defining property of the play | Implementing path **plus** the named absent property | 3 |
| **Absent** | No counterpart | A reproducible search over `.claude/commands/` and `.claude/make-it/references/` returning zero matches | 5 |
| | | **Total** | **12** |

Adjectives such as "weak", "immature" or "poor" are not used. They are not
reproducible.

### 0.4 Finding count differs from play count — deliberately

The 8 non-Present plays yield **9 findings** (`G01`–`G09`). One play —
*Hooks as approval gates* — splits into two findings (`G07`, `G08`) because they
require different fixes at different privilege levels: `G07` is a repository
commit, `G08` requires MDM/organisation administration. Per the reporting
standard, findings needing different fixes are counted separately even where a
reader would see one topic.

Reconciliation: **12 plays → 4 Present + 8 non-Present → 9 findings.**

### 0.5 Scope boundary

In scope: the `make-it` repository at the commit above — `.claude/commands/`,
`.claude/make-it/`, `.github/`, `docs/`, root configuration.

Out of scope, and therefore not evidence for any verdict:

| Excluded | Reason | Privilege that would bring it in scope |
|---|---|---|
| Applications generated by `/make-it` | Live in other repositories | Read access to those repositories |
| `.claude/plugins/**` | Third-party plugin cache, not this project's code | n/a |
| GitHub organisation settings, branch protection, required reviewers | Not observable from a checkout | GitHub organisation **owner** or repository **admin** |
| Claude Code enterprise managed settings (`allowManagedHooksOnly`, `disableSideloadFlags`) | Distributed by MDM, never committed | MDM administrator **and** Claude Code Console admin |
| `/Users/<user>/.claude/**` user-level settings | Per-machine, not shipped with the framework | Local shell on each engineer's machine |

Where a control could only exist out of scope, the finding is marked
**UNOBSERVED**, not Absent. Exactly one finding (`G08`) carries that mark.

### `G01` — No durable intent artifact; no recorded accept/reject decision

**Verdict:** Absent · **Stage:** Plan · **Severity:** High (audit), Low (function)

**What the problem is.**
The playbook's Plan stage produces `intent.md` — a committed, version-controlled
proto-specification with fixed sections (Problem, Proposed outcome, Affected
users and systems, Constraints, Open questions, Metadata). Its function is not
documentation. Its function is that the product owner's **merge or close is the
stage-gate record**, and the merge is what triggers Design. The playbook's Plan
stage is artifact-triggered.

`/make-it` Phase 1 (Ideation) conducts the equivalent conversation — plain-English
Q&A, one question at a time — and writes nothing durable from it. Phase transition
is *command-triggered*: the user types the next slash command. There is no
artifact, therefore no merge, therefore no record of who decided to proceed.

**Where the problem is.**

| Location | Observation |
|---|---|
| `.claude/commands/make-it.md` — Phase 1 (Ideation) | Conversational only; no write step for intent |
| `.claude/commands/retrofit-it.md` — Phase 3 (Clarification) | Same pattern; max 3–5 questions, no artifact |
| Search: `intent\.md\|spec\.md\|plan\.md` over `.claude/commands/` + `.claude/make-it/references/` | **0 matching lines** (Appendix §D) |

**How to address it.**
1. Add `intent/` to the generated project's directory layout in
   `.claude/commands/make-it.md` Phase 1.
2. At the end of Ideation, write `intent/<slug>.md` with the playbook's six
   sections, populated from the Q&A already captured in context.
3. Record the sponsor and timestamp in the Metadata section.
4. Optional, and a process decision rather than a technical one: require the file
   to be merged before Phase 2 begins. For a single-user workflow this reduces to
   an explicit in-session confirmation, which `/make-it` already performs — the
   change is that the confirmation becomes a committed record.

Effort: template + one write step. No new dependency.

### `G02` — Design output has no specification document and no human approval gate

**Verdict:** Partial · **Stage:** Design · **Severity:** Medium

**Named absent property:** *product-owner approval recorded against a
specification that is reviewable before Build starts.*

**What the problem is.**
The playbook's Design stage emits `spec.md`, checked against organisational
skills (brand, security, compliance, UX), with contradictions between policies
**explicitly flagged rather than silently resolved**. `spec.md` and `intent.md`
are then committed as a pair, and a human — consulting technical leads for
higher-risk items — decides whether Build proceeds.

`/make-it` does produce a design artifact. `app-context.json` records the
technical decisions, and `CLAUDE.md` describes Phase 2 as *"AI-driven technical
decisions (invisible to user)."* Two properties of the playbook's play are
missing, and the second is the material one:

1. There is no human-readable narrative specification — `app-context.json` is a
   decision record, not a design document.
2. **"Invisible to user" means no review point exists.** There is nothing for a
   product owner to approve, and no flagging mechanism for irreconcilable policy
   conflicts.

**Where the problem is.**

| Location | Observation |
|---|---|
| `.claude/make-it/templates/app-context.md` | Template for the decision record; no narrative spec, no approval field |
| `.claude/commands/make-it.md` — Phase 2 (Design) | Explicitly non-interactive |
| `/Volumes/PRO-BLADE/make-it/CLAUDE.md` — "How It Works", step 2 | `"Design -- AI-driven technical decisions (invisible to user)"` |
| `.claude/make-it/references/design-blueprint.md` (157 KB) | The policy corpus the spec would be checked against — exists, but nothing emits a conformance statement |

**How to address it.**
1. Emit `spec.md` alongside `app-context.json` at the end of Phase 2 — same data,
   prose form, written for a reader rather than a parser.
2. Add a **Conflicts** section that is populated when two policies in
   `design-blueprint.md` or `guardrails.md` cannot both be satisfied. Today such
   a conflict is resolved silently by the model; surfacing it is the higher-value
   half of this finding.
3. Add an `approved_by` / `approved_at` pair to the `app-context.json` schema in
   `.claude/make-it/templates/app-context.md`.
4. Retain the "invisible" default for the single-user path. Make the review point
   opt-in via a flag rather than mandatory, so the non-technical user experience
   that `/make-it` exists to provide is not degraded.

### `G03` — Plan mode is not the Build entry point

**Verdict:** Absent · **Stage:** Build · **Severity:** Low

**What the problem is.**
The playbook makes Claude Code's plan mode the default start of Build: the model
produces a plan, a human approves it, and only then does the model write. It is
the last cheap intervention point before code exists.

`/make-it` enters Build directly. The intervention that plan mode provides is
partly substituted by the scaffold — for scaffolded paths the plan is effectively
fixed in advance, which is a legitimate substitute. It is *not* substituted for
the domain-specific code generated on top of the scaffold, which is where the
per-application variability actually lives.

**Where the problem is.**

| Location | Observation |
|---|---|
| Search: `[Pp]lan mode\|EnterPlanMode\|ExitPlanMode` over `.claude/commands/` + `.claude/make-it/references/` | **0 matching lines** (Appendix §D) |
| `.claude/commands/make-it.md` — Phase 3 (Build) | Proceeds directly from Design |
| `.claude/commands/retrofit-it.md` — Phase 4 (Plan) | Presents a retrofit plan and takes approval — the closest existing analogue, and evidence the pattern is already acceptable in this framework |

**How to address it.**
Adopt the `retrofit-it` Phase 4 pattern for the *domain-code* portion of
`/make-it` Build only. Do not gate scaffold copy — it is deterministic and
reviewing it wastes a gate. Lowest-cost option: reuse the existing
`retrofit-it.md` plan-presentation block rather than writing a new one.

### `G04` — Institutional knowledge is packaged as commands, not as auto-triggering Skills

**Verdict:** Partial · **Stage:** Build · **Severity:** Medium

**Named absent property:** *context-triggered activation.*

**What the problem is.**
The playbook's model: encode knowledge in `SKILL.md` with frontmatter declaring
**triggers**, store at `.claude/skills/<name>/`, and the skill fires automatically
when the described situation arises. Its example — `secure-api-review`, firing on
endpoint creation — is the whole point: the engineer does not have to know the
policy exists.

`/make-it` has the knowledge. It has a great deal of it: 14 command files and
599 KB across 15 reference files, with `build-standards.md` (101 KB) explicitly
designated single source of truth and consumed by three skills. What it lacks is
automatic activation. Every one of the 14 is invoked by a human typing `/name`.
The reference corpus loads only when an invoked command reads it.

Consequence: policy in `guardrails.md` and `build-standards.md` is unreachable
during any session where the user did not type the right command — including
ordinary Claude Code sessions in a `/make-it`-generated project.

**Where the problem is.**

| Location | Observation |
|---|---|
| `.claude/commands/` (14 files — full list in Appendix §A) | Slash-command form; user-invoked |
| `.claude/skills/` | Does not exist |
| `.claude/make-it/references/guardrails.md` (61 KB) | Read only via an invoking command |
| `.claude/make-it/references/build-standards.md` (101 KB) | Same |

**How to address it.**
1. Extract the trigger-shaped subsets of `build-standards.md` and `guardrails.md`
   into `.claude/skills/<name>/SKILL.md` with frontmatter triggers. Candidate
   first cut: the Tier 0 universal checks and the Tier 1 auth/RBAC checks, since
   those apply regardless of which command is running.
2. Leave the 14 commands as-is. They are workflows, not policies; the slash-command
   form is correct for them.
3. Note the playbook's own caveat, which applies directly here: *"Skills make
   policy compliance likely… A policy that must always hold needs something
   deterministic behind the skill."* This finding raises the probability of
   compliance. It does not enforce it. Enforcement is `G07`.

### `G05` — No eval suite; framework changes ship unverified

**Verdict:** Absent · **Stage:** Test · **Severity:** High

**What the problem is.**
The playbook describes continuous evals as *"the AI-native equivalent of
stage-gate QA"*: 20–50 real tasks with acceptance criteria, run non-interactively
in CI, re-run **whenever `CLAUDE.md`, skills or hooks change**, with merge blocked
on pass-rate regression, and every production incident converted into a permanent
eval.

That trigger condition is exactly this repository's change pattern. `/make-it`
ships agent configuration as its product: 14 skills, 599 KB of references, 199
scaffold files. Editing `guardrails.md` or `build-standards.md` alters the
behaviour of every future build, and nothing verifies the alteration.

`/make-it` does test the *applications* it generates — build-verify Parts A–D,
the security self-healing loop, `try-it` smoke tests, `resume-it` pytest/Playwright
scaffolding. That is application testing. It runs inside a build, after the
framework change has already taken effect. It cannot catch a framework regression
before merge, because it does not run at merge.

**Where the problem is.**

| Location | Observation |
|---|---|
| Search for `evals`/`eval`/`*.eval.json` files or directories | **0 found** (Appendix §E) |
| Prose occurrences of `eval`/`evals`/`evaluation` in commands + references | **9 lines** — English usage, not a suite (Appendix §D) |
| `.github/workflows/` | **1 workflow**: `manifest-check.yml` — validates the content manifest, asserts nothing about build behaviour (Appendix §G) |
| `.claude/make-it/scaffolds/` | **199 files** (122 `fastapi-nextjs`, 67 `nextjs-fullstack`, 10 `overlays`) with no build regression test |

**How to address it.**
1. Create `evals/` with 20–50 task definitions. Acceptance criteria per the
   playbook: tests pass, lint clean, behaviour unchanged, policy compliance.
2. Seed the corpus from this repository's own history at zero authoring cost —
   commits `#11`–`#15` are each a real, already-diagnosed regression
   (dependency pinning, installer idempotency, Windows one-liner safety).
3. Add `.github/workflows/evals.yml`, triggered on push affecting `.claude/**`
   plus a schedule, running Claude Code non-interactively.
4. Gate merge on pass rate. Log runs so the rate is comparable over time.
5. Adopt the incident→eval rule: every future fix commit adds its eval in the
   same PR.

Prerequisite for `G07` and `G03` to be attempted safely: without this, there is
no way to confirm a hook or a new gate has not broken the 199-file scaffold path.

### `G06` — No policy-based AI review of proposed changes

**Verdict:** Partial · **Stage:** Deploy · **Severity:** Medium

**Named absent property:** *review of the completed change against a written
review policy, in CI, visible on the pull request.*

**What the problem is.**
The playbook splits this into: Claude reviews incoming PRs against organisational
policy; Claude also responds to review comments on its own PRs; the policy lives
in `REVIEW.md` with multiple passes (bugs, security/injection, spec and design
conformance, edge cases and regressions); findings are severity-ranked with caps
on Nits; and critically, **findings neither approve nor block — branch protection
still requires a code owner.**

`/make-it` has a genuine and useful counterpart: `/ship-it`'s Pre-Push Self-Review,
six checks run before every push, plus post-push CI monitoring with auto-fix. Two
properties differ:

1. It is **pre-push and local** — it inspects the working tree, not the pull
   request, so its findings are not visible to a reviewer.
2. Its six checks are **mechanical, not policy-based** — lint/type-check, env-var
   cross-check, migration-chain integrity, import/dependency check, secret-leak
   scan, build verification. None of them evaluates the change against
   `design-blueprint.md`, `guardrails.md` or `build-standards.md`. Design
   conformance is unreviewed.

**Where the problem is.**

| Location | Observation |
|---|---|
| `.claude/make-it/references/ship-it-guide.md:81` | Pre-Push Self-Review — 6 mechanical checks, local, pre-push |
| `.claude/make-it/references/ship-it-guide.md:102` | Post-Push CI Monitoring — watches and auto-fixes CI failures; does not review content |
| Search: `claude-code-action\|REVIEW\.md` over `.github/` + commands + references | **0 matching lines** (Appendix §D) |
| `/Users/<user>/.claude/ship-it/templates/` | 7 templates (`ship-it.yml`, `ship-it-aws.yml`, `ship-it-azure.yml`, `ship-it-azure-aca.yml`, `workflow.yml`, `pr-description.md`, `checklist-prod.md`) — none invokes a review action |

**How to address it.**
1. Author `REVIEW.md` from the existing corpus. The passes map directly onto
   material already written: security → `build-verify-security.md`; spec
   conformance → `build-standards.md` check IDs; design → `design-blueprint.md`.
2. Add `claude-code-review.yml` to `/Users/<user>/.claude/ship-it/templates/` so
   generated projects inherit it. A working reference implementation is already
   present on this machine at
   `.claude/plugins/marketplaces/claude-code-skills/.github/workflows/claude-code-review.yml`
   — adapt rather than author.
3. Keep the playbook's constraint: advisory findings only. Approval authority
   stays with branch protection and a code owner.
4. Retain the Pre-Push Self-Review unchanged. It catches a different class of
   defect earlier and more cheaply; this finding adds a layer, it does not
   replace one.

### `G07` — 203 enforcement-tagged rules with no deterministic enforcer

**Verdict:** Absent · **Stage:** Deploy (applies framework-wide) · **Severity:** High

**This is the highest-value finding in the assessment.**

**What the problem is.**
The playbook is unambiguous: *"A policy that must always hold needs something
deterministic behind the skill, such as a hook that blocks the action."* Hooks
are scripts registered in `.claude/settings.json`, matched on a tool event such
as `PreToolUse`, returning allow / block / ask. Exit code 2 blocks with a message.
Allow and block decisions are logged with timestamps, which is what produces an
audit trail.

`/make-it` declares a severity taxonomy — `[BLOCK]` ("must pass before handoff"),
`[FIX]` ("auto-fix if failing"), `[WARN]` ("note in TODO.md") — and applies it
203 times in the enforcing tiers. Every one of those 203 is enforced by the model
reading English prose and choosing to comply. There is no mechanism that fails
closed.

`[WARN]` is excluded from the 203; it is advisory by design and correctly
implemented as prose.

**Where the problem is.**

| Location | Observation |
|---|---|
| `.claude/make-it/references/*.md` — `[BLOCK]` | **75 occurrences** (Appendix §H) |
| `.claude/make-it/references/*.md` — `[FIX]` | **128 occurrences** (Appendix §H) |
| **Total asserting enforcement** | **203** |
| `.claude/make-it/references/*.md` — `[WARN]` | 7 occurrences — correctly advisory, excluded |
| `.claude/settings.json` | **Does not exist** (Appendix §F) |
| `.claude/hooks/` | **Does not exist** (Appendix §F) |
| `.claude/settings.local.json` | Present — permissions only; **0** hook event keys (Appendix §F) |

Note on interpretation, carried identically in the briefing: 203 counts
*assertions in text*, not 203 distinct controls. Several are the same control
restated per tier or per project type. De-duplicating them is the first task of
the fix, not a correction to the count.

**How to address it.**
1. De-duplicate the 75 `[BLOCK]` assertions into the distinct controls they
   represent. Expect materially fewer than 75.
2. Rank by what is (a) mechanically checkable and (b) expensive if violated. The
   secret-leak check is the obvious first — it already exists as prose at
   `ship-it-guide.md:81` check 5, including the `sk-ant-oat` / `CLAUDE_CODE_OAUTH_TOKEN`
   subscription-token case, and moving it from prose to a hook converts the
   single highest-consequence rule in the framework from a sign to a lock.
3. Create `.claude/settings.json` with a `PreToolUse` matcher on `Bash` (and
   `Edit`/`Write` where the control is about file content), pointing at scripts
   in `.claude/hooks/`. Exit 2 to block, with a plain-language message consistent
   with the framework's user-facing tone.
4. Ship the same hooks into generated projects via the scaffold, so enforcement
   applies where the code actually gets written — not only in this repository.
5. Sequence after `G05`. A hook that blocks incorrectly is worse than no hook,
   and the eval suite is what proves it does not.

### `G08` — Enterprise governance controls unobserved

**Verdict:** UNOBSERVED · **Stage:** Deploy · **Severity:** Cannot be assessed

**What the problem is.**
The playbook's governance layer is delivered through **managed settings**,
distributed by platform teams via MDM and not committable to a repository:
`allowManagedHooksOnly` (restricts hooks to platform-approved versions),
`permissions.deny` and `sandbox` (layered blocking at tool and OS level),
`credentials` (denies access to sensitive files and environment variables),
`disableSideloadFlags` (prevents circumvention of installed plugins).

**Where the problem is.**

| Location | Observation |
|---|---|
| Search for managed-settings keys in committed settings | **0 occurrences** (Appendix §F) |
| `.claude/settings.json` | Does not exist |

**Why this is not scored as Absent.** Managed settings are *designed* not to
appear in a repository. Their absence here is the expected state and carries no
information about whether they are deployed. Recording this as "Absent" would be
an unsupported claim.

**What closes this gap — exactly.**
- **Claude Code Console administrator** access, to read the organisation's
  managed-settings policy.
- **MDM administrator** access (Jamf / Intune / equivalent), to confirm the
  policy is actually distributed to engineer machines.
- **GitHub organisation owner** or repository **admin**, to read branch
  protection and required-reviewer configuration — which `G06` step 3 depends on.

Until all three are available, the correct statement is *not assessed*. No
remediation is proposed, because no defect has been established.

### `G09` — No production metrics loop

**Verdict:** Absent · **Stage:** Maintain · **Severity:** Medium

**What the problem is.**
The playbook's Maintain stage closes the cycle. Pick **one** metric with a stable
baseline (CI test failure rate, post-deploy 5xx rate, or PR cycle time). A
deterministic script watches it against a rolling 30-day baseline using
statistical rules — the playbook names Western Electric — to catch both spikes
and slow drift. A breach invokes Claude at a severity tier (log / diagnose /
propose). Claude writes the finding as `intent.md`, which re-enters Stage 1, and
the eventual fix adds an eval so the incident cannot recur silently.

`/make-it` has no part of this. Stage 6 is the only playbook stage with no
counterpart of any kind.

**Where the problem is.**

| Location | Observation |
|---|---|
| Search: `cycle time\|DORA\|lead time\|telemetry\|rolling baseline\|Western Electric` over commands + references | **2 matching lines in 2 files** (Appendix §D) |
| `.claude/commands/nemo-it.md` | 1 line — security-attestation context, not operational monitoring |
| `.claude/make-it/references/git-operations.md` | 1 line |
| `.claude/commands/resume-it.md` — Phase 4 (Readiness Check) | Nearest analogue: standup-style status, generates `NEXT-STEPS.md`. Reads repository state, **not** production telemetry. Not a loop |

**How to address it.**
1. Pick one metric. Recommend **CI test failure rate** — it is already emitted by
   `.github/workflows/`, needs no production access, and is the cheapest possible
   starting baseline.
2. Write a deterministic detector script with a 30-day rolling window.
3. On breach, have it write `intent/<incident>.md` — which is `G01`'s artifact.
   `G01` is therefore a prerequisite, and doing `G01` first makes `G09` largely a
   detector script rather than a new subsystem.
4. On fix, add the eval — which is `G05`'s suite. `G05` is the second prerequisite.
5. Track the two indicators the playbook specifies: time from breach to queued
   `intent.md` (leading); share of findings that become merged fixes, and
   repeat-incident rate (lagging).

## 3. Dependency order

The findings are not independent. This is the order in which they are safe and
cheap to attempt.

```
G05 (eval suite)  ─────┬──► G07 (hooks)        proves a hook has not broken the build path
                       ├──► G03 (plan mode)    proves a new gate has not broken the build path
                       └──► G04 (Skills)       proves extracted skills still trigger correctly

G01 (intent artifact) ─┬──► G02 (spec + approval)   spec is written against a committed intent
                       └──► G09 (metrics loop)      breach output needs somewhere to land

G07 (hooks) ───────────────► G06 (AI PR review)     reviewer needs firm rules to check against

G08 (managed settings) ── blocked: requires MDM + Console + GitHub org admin
```

Recommended first two, and then reassess: **`G05`, then `G07`.** Together they
convert the framework from unverified-and-unenforced to verified-and-enforced,
which is the change that makes every remaining finding cheaper.
